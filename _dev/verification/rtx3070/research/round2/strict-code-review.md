## Findings

1. **[P1] Set and record the verified Torch precision policy in the actual trainer.** `training/wanda_bonsai2/src/archie_wanda/worker.py:237` seeds and constructs the CUDA suffix/head without setting the matmul precision policy. In contrast, `verification.py:64` and `verification.py:203` explicitly select `highest`. The new admission always labels this worker `strict-f32`, but that label does not constrain the process-global Torch policy or a TF32 override. If the worker inherits a lower-precision policy, its attention and LoRA matrix multiplies can use a different numerical path than the successful reference while the run still claims strict admission. Before the first allocation/forward, explicitly select and verify highest/TF32-off, reject conflicting process overrides rather than change other applications' settings, and include the effective settings in the run identity/checkpoint/receipt. This is the blocker for the next two-update run; relying on today's default is insufficient to preserve the newly required precision contract.

2. **[P2] Validate the extraction/backward evidence rather than only their labels.** `training/wanda_bonsai2/src/archie_wanda/admission.py:23` checks no extraction cases/comparisons, and lines 30–33 check no backward steps, losses, gradients, vocabulary, token count, or measured Torch precision. CPU reproduction using the new `TrainingAdmissionTests.setUp()` fixture calls `validate_gates(test.config, test.spec)` successfully even though extraction has no `cases` and backward has no `steps`. Consequently a partial or mislabeled receipt can admit semantic training without the required three-case native proof and two finite updates. Require the expected nonempty extraction evidence and original finite RMS/KL bounds, plus two finite backward records, full vocabulary, valid token count, complete expected gradient names, and nonzero A/B gradients on step two. Reject absent and nonfinite fields. This is an ordinary incomplete-receipt case, not a demand for signed JSON or protection against a deliberately fabricated measurement.

3. **[P2] Reject nonfinite native comparison metrics explicitly.** `training/wanda_bonsai2/src/archie_wanda/native.py:194` through line 201 use only `metric > threshold`; NaN makes every such comparison false. CPU reproduction with NaN in all reset/microbatch `relative_rms` fields and `max_token_kl` returns normally from `judge_native_comparisons(..., 'strict-f32')`. Validate numeric type, finiteness, and valid range before applying the original bounds, and add a negative test. The current extraction producer also checks finite cache payloads, so this does not establish that an existing real receipt passed on NaN; it establishes that this gate itself fails open on the requested malformed numerical input.
