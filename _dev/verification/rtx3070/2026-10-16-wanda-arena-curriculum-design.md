# Wanda progressive curriculum and local AI Arena — owner amendments

Scope: the three plan changes requested2026-10-16, for active Wanda PR38. This is an implementation specification, not evidence that a runner is installed or that any arm won. The [trainer plan](2026-10-16-wanda-trainer-plan.md) and [benchmark plan](2026-10-16-wanda-benchmark-plan.md) retain their native parity/backward gates.

## Critical path stays short

Order: exact base/PTQ checks → complete native extraction → zero/nonzero suffix parity → complete loss/backward → two real optimization updates on a small admitted social shard → checkpoint/native reload → bounded initial semantic run. Use fully formed, short project-owned examples for that shard, not random projection targets, fabricated metrics or a full book-corpus dependency. Label two updates training-mechanics evidence, not social competence.

Corpus expansion, CLI-agent adapters and Cortex decision transport follow independent tracks. They cannot become start conditions for those initial tests. No requirement to wait for51books,128completed families, all providers, human benchmark ratings, an IRIS Rust port or GUI/WSL work before testing the numerical training path. Resource/authority/parity checks still apply; do not bypass them to report progress.

## Progressive dataset and generalization

128training families plus32development families remain the first tranche. Expansion has no lifetime family-count ceiling. Candidate tranches of up to128new families are reviewed and admitted only if their causal mechanisms and annotations add coverage; smaller high-quality tranches are preferred to low-quality padding. Cosmetic variants do not count as new families. Book count, token count and number of automatically generated rows are descriptive quantities, not optimization targets.

Track a causal coverage ledger: user's objective and horizon; stakeholder knowledge/beliefs; prior commitments and relationship history; power/dependence; conflicting incentives; observability/missing evidence; time/resource constraints; culture/language; setting and communication channel; and consequences. Cover friendship/family, work teams, sales/negotiation, reputation/groups and unfamiliar mixed contexts. Include ambiguous and adversarial testimony, strategic omissions, contradictory accounts, unreliable narrators, quoted instructions and irrelevant emotional/contextual noise. A counterfactual must change an identified causal variable; the annotation says whether the action, rationale or confidence should change.

Every admitted family has source/author/edition or owned-synthetic provenance, domain, family ancestry, difficulty, causal variables, applicable evidence, concise decision justification, alternatives, outcomes/forecast definitions where known, and uncertainty. Reviews reject label contradictions, ungrounded certainty, copy/translation leakage and broken target truncation. They do not assign a moral admissibility label. Keep failures of admired techniques and successful counterexamples to common heuristics, including techniques from darker influence literature, with their conditions/uncertainty.

Development reports separate noise invariance from sensitivity to decisive evidence, novel-family/novel-combination generalization, forecast calibration where resolved, and strategic consequences. Examine family-level error clusters when metrics plateau. Distinguish label/rubric ambiguity, insufficient causal coverage, prompt truncation, capacity and optimization failure before adding data/layers. Run an ablation with/without the new tranche, same base/settings/seed and development family set; repeat a second seed before treating a small gain as repeatable. Training loss, JSON rate and a flattering aggregate cannot trigger expansion by themselves.

Freeze each tranche and its split digest before a run. Source-derived/paraphrased/translated relatives remain together. Keep a stable development anchor plus a separately reported fresh-development tranche, so replacing easy/hard cases cannot masquerade as improvement. Sealed benchmark cases/keys/results never feed the ledger's labels or checkpoint/rank/target choice. Once seen, a held-out set becomes exploratory and requires replacement for the next confirmatory claim. Publish admitted/rejected/pending counts and reasons separately from model scores.

## Reuse the existing Arena

Existing `core/crates/archie-arena` is a Stage desktop-task evaluator. `model.rs::Nebius::ask` currently includes model fallback, which must not be reused silently for exact-model comparisons. `live.rs` and `archie-arena-live` already support IRIS `/act` decisions carried through Stage. Preserve their desktop task/action gate and do not substitute this Stage runner for the user's Archie desktop GUI.

Add a common arena registry at the evaluation layer, leaving existing Stage tasks intact. Every discovered local-use assistant is represented explicitly with execution host, inference locality (`local`, `remote`, `unknown`), actual model/runtime identity, supported capabilities, credential readiness, allowed tools, resource/concurrency limits, protocol version and adapter state. A locally launched Codex/Claude client can call a remote model; calling it local inference would be false.

Required adapter kinds: `native_bonsai`, `codex_cli`, `claude_code_cli`, `iris_http`; direct provider arms remain available for the original exact-model research comparison. States: discovered→capability_checked→ready→running→completed, or unavailable/auth_required/incompatible/budget_exhausted/failed. Discover actual executables/endpoints without reading secret contents or installing replacements. Every discovered assistant appears in the inventory; an absent or unsupported capability yields not_run/not_applicable, never a fabricated response or silent substitute.

Three labelled tracks:

1. **Social model track:** exact Wanda/base9B/27B/Opus5.5/Sol direct model interfaces with the common no-tools prompt/budget. This preserves the original confirmatory comparison.
2. **Agent track:** Codex, Claude Code and other discovered local-use agents run the same public social/problem-solving tasks in ephemeral isolated workspaces with declared tool/context budgets. A no-tools condition is valid only if the CLI truly disables tools and the environment enforces isolation; read-only file access alone does not establish that. Record agent scaffolding, hidden/default prompts, actual model identity, tool traces and remote inference. Results cannot stand in for the direct API arms. Do not silently run agents on the repo, user's home, existing chat memory or sealed answer keys.
3. **IRIS perception/action track:** replay admitted synthetic/public observations and goal/feedback cases using existing IRIS endpoints and Stage gates where actions are needed. Record perception/action correctness, recovery and real latency. An IRIS control head is not automatically a language adviser; social-language scores are not_applicable unless a verified compatible adviser interface exists. An IRIS-plus-planner system is a separately named composite arm with both identities and costs.

Autonomous execution means a bounded queue with one GPU owner at a time, immutable case/settings digests, time/token/tool/cost caps, per-case receipts, checkpoint/resume and stop on authority/resource failure. It does not mean unlimited subscriptions, indefinite retries or unreviewed execution on the desktop. A model under test must not grade its own decisions. CLI agents may solve benchmark tasks; they do not author sealed labels or alter training/configuration.
